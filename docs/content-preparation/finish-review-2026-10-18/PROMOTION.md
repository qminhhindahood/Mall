# Prepared promotion, dry run only

`node docs/content-preparation/finish-review-2026-10-18/promotion-dry-run.mjs` uses the **actual** `validateContent` and research importer functions under Node 26 type stripping, without a build. It reads accepted private geometry/decisions and current display holds, then clears fixture flags in a fresh structural proposal. It writes only `dry-run/` here, never application `data/`, source, existing ledgers or dist. In-memory software-only fixtures validate the complete candidate structure with fixture-scoped review metadata; that metadata is neither editorial approval nor persisted into a proposed public snapshot. No-approval execution intentionally fails public candidate validation (`actual snapshot review date required`) and confirms valid empty pending snapshots still pass. Receipt records all outcomes honestly.

The structural proposals contain 165 Saigon / 203 Vincom destinations, three Highlights each, current supported held-filtered areas only and null-photo treatment. Included expanded candidates absent from the306-record preview get floor-only access; no geometric guess. Held broad parents and L5-05 are excluded by the exact incumbent importer. Expanded `category-pending` stays explicitly **Chưa phân loại / Uncategorised**, rather than invent a category; batch taxonomy acceptance must cover this visible group. Three identity holds are excluded completely. Facilities remain empty.

Actual content schema supports Highlights references (`destinationId`, `categoryId`, `floorId`, `review`) only. The rich VI/EN nomination titles/descriptions are review copy in `highlights.json`; they are **not silently imported** into an unsupported schema field. Current UI uses destination descriptions for the cards. If custom recommendation prose is desired on production cards, that requires a separately reviewed schema/UI change before final build. The six references themselves are immediately representable after acceptance.

To prepare approved-shaped private output later, pass `--approval <actual-decision.json>`. The file must bind exact `roster`, `highlights`, `holds` hashes from `dry-run/receipt.json` and include per-mall explicit true values for `rosterApproved`, `copyApproved`, `taxonomyApproved`, `statusesConfirmed`, `highlightsApproved`, `noFacilitiesApproved`; real `source`, `rosterReviewedBy`, `reviewedAt`; actual `languages.vi/en.reviewedBy/reviewedAt`; and either a reviewed `statusById` map or explicit `allIncludedStatusesOpen: true`. Optional `excludeIds`/`excludeHighlightIds` support batch corrections by exception. Do not fill approval metadata from this plan or from an AI test. No ready-to-run fake approval example is supplied.

The script rejects mismatched hashes, missing reviewers/dates, unknown categories, Highlights pointing to excluded destinations, any actual validator failure and accidental public fixture flags. It can emit **approved-shaped private candidate files only**, not publication approval or data writes. Date values must come from the actual decision record. This does not substitute the owner's actual review or approve occupancy from old maps.

After real decisions, the integration owner reviews the emitted JSON and paired geometry diffs. The accepted additional geometry is needed if its independent area IDs are retained; do not copy the directory against an older geometry revision. Preserve all original regions and later display holds. Apply the accepted snapshot/geometry as a separate, reviewable application commit; run the six exact builds and required visitor/runtime/transport checks; propagate shared implementation to both site branches with mall-specific data isolated; then request release authorization for the named HTTPS targets. This script intentionally has no apply or deploy command.
